# Task Manager

A small full-stack task manager. You can create, view, update and delete tasks.

- **`backend/`**: a Spring Boot REST API (Java 17, Spring Web, Spring Data JPA, H2), packaged as a Docker image.
- **`frontend/`**: a React client (Vite) that calls the API.

## Quick start

You need Docker, and Node.js 18+ with npm.

**1. Start the API in Docker** (from the project root):

```bash
docker compose up --build
```

**2. Check that the API responds:**

```bash
curl http://localhost:8080/api/tasks
# []
```

**3. Start the React app** (in a second terminal):

```bash
cd frontend
npm install
npm run dev
```

**4. Open the app:** go to http://localhost:5173.

Stop the API with `Ctrl+C`, or with `docker compose down`. Data lives in an H2 in-memory database, so it resets whenever the container restarts.

## Backend

### Run with Docker (without Compose)

```bash
cd backend
docker build -t task-manager-backend .
docker run --rm -p 8080:8080 task-manager-backend
```

The `Dockerfile` is a multi-stage build. A Maven stage compiles and packages the jar, and a slim Java 17 runtime image runs it.

**If the build fails with `DependencyResolutionException`:** Maven inside the build container couldn't reach Maven Central. This is usually a Docker DNS problem on the host. Build with the host's network instead:

```bash
docker build --network=host -t task-manager-backend .
```

### Run without Docker

You need Java 17+ and Maven 3.6.3+.

```bash
cd backend
mvn spring-boot:run
```

### Tests

```bash
cd backend
mvn test
```

The integration tests (`src/test/java/.../TaskControllerTest.java`) start the full application with H2. They check every endpoint, the status codes, validation, the error body and CORS.

### API

Base URL: `http://localhost:8080/api`

| Method | Endpoint           | Success          | Errors                        |
|--------|--------------------|------------------|-------------------------------|
| GET    | `/api/tasks`       | `200 OK`         | none                          |
| GET    | `/api/tasks/{id}`  | `200 OK`         | `404` if the task is missing  |
| POST   | `/api/tasks`       | `201 Created`    | `400` if the input is invalid |
| PUT    | `/api/tasks/{id}`  | `200 OK`         | `400` if invalid, `404` if missing |
| DELETE | `/api/tasks/{id}`  | `204 No Content` | `404` if the task is missing  |
| POST   | `/api/images`      | `201 Created`    | `400` if not a valid image, `413` if over 2 MB |
| GET    | `/api/images/{id}` | `200 OK`         | `404` if the image is missing |

The two image endpoints support pictures in task descriptions. See [Rich-text descriptions](#rich-text-descriptions).

**Create a task:**

```bash
curl -i -X POST http://localhost:8080/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "Prepare report", "description": "Draft weekly report", "status": "TODO"}'
```

```http
HTTP/1.1 201
Location: /api/tasks/1

{"id":1,"title":"Prepare report","description":"Draft weekly report","status":"TODO"}
```

**Task fields:**

| Field         | Type   | Rules                                              |
|---------------|--------|----------------------------------------------------|
| `id`          | Long   | Generated by the server                            |
| `title`       | String | Required, 3–100 characters (surrounding spaces are trimmed) |
| `description` | String | Optional rich text (HTML). At most 500 visible characters; markup doesn't count. Empty content is stored as `null` |
| `status`      | Enum   | `TODO`, `IN_PROGRESS` or `DONE`. Defaults to `TODO` on create |

On `PUT`, leaving out `status` keeps the task's current status. This way, editing a title never silently resets progress.

**Errors:** every error, including a bad id such as `/api/tasks/abc`, an unknown path, or an unsupported method, returns the same JSON shape:

```json
{
  "timestamp": "2026-10-09T06:47:33.954Z",
  "status": 400,
  "error": "Bad Request",
  "message": "title must be between 3 and 100 characters",
  "path": "/api/tasks"
}
```

### Rich-text descriptions

The description editor supports bold, italic, underline, strikethrough, inline code, code blocks, bulleted and numbered lists, font family, font size and images. The description is stored as HTML, so it's treated as untrusted input:

- **Sanitized on save:** `HtmlSanitizer` (built on jsoup) keeps only the tags the editor produces. Scripts, event handlers and links are removed, inline styles are limited to `font-size` and `font-family` with safe values, and `<img>` is kept only when it points at `/api/images/{id}`.
- **Sanitized again on display:** the frontend runs DOMPurify before rendering.
- **Length:** the 500-character limit counts visible text, checked by a custom `@MaxTextLength` constraint. The stored HTML has a separate cap of 5000 characters.

**Images:** `POST /api/images` takes a multipart `file` field: PNG, JPEG, GIF or WebP, up to 2 MB. The type is detected from the file's bytes, not the client's claim, and SVG is rejected because it can carry scripts. The response is `{"id": 1, "url": "http://localhost:8080/api/images/1"}`, and the editor inserts that URL. Images are stored in H2, so like tasks they reset on restart.

```bash
curl -i -F "file=@screenshot.png" http://localhost:8080/api/images
```

**CORS:** the API accepts requests from the React dev server at `http://localhost:5173`. You can change this with `app.cors.allowed-origins` in `application.properties`.

### Design

The code follows a Controller → Service → Repository structure:

- **`controller/`:** HTTP mapping only, and it returns the correct status codes. `TaskController` and `ImageController`.
- **`service/`:** business rules, such as the default status, keeping the status on update, sanitizing descriptions, validating uploads, and not-found handling.
- **`repository/`:** Spring Data JPA repositories for the `Task` and `Image` entities.
- **`dto/`:** `TaskRequest` (with validation), `TaskResponse`, `ImageResponse` and `ErrorResponse`. The JPA entities are never exposed by the API.
- **`exception/`:** `GlobalExceptionHandler`, which maps every error to the shared JSON body.
- **`util/`:** `HtmlSanitizer` for rich-text descriptions.
- **`config/`:** the CORS setup.

## Frontend

```bash
cd frontend
npm install
npm run dev      # http://localhost:5173
npm run build    # production build into dist/
```

The app expects the API at `http://localhost:8080/api`. It provides:

- **Task list:** shows each task's title, formatted description and status.
- **One form for create and edit:** **Edit** loads a task into the form, including its status. The description uses a rich-text editor ([TipTap](https://tiptap.dev)) with a formatting toolbar and image upload. It grows with its content, then scrolls.
- **Delete:** asks for confirmation in a modal dialog first.
- **Responsive layout:** two columns on desktop, one column on phones.
- **Up-to-date list:** the list reloads from the API after every successful create, update or delete.
- **Feedback:** field validation messages (mirroring the API rules), a loading state, and a "Saving…" state on the submit button. A success message confirms each change, and any API error is shown with its message.
